# RONIN

RONIN is a lightweight cloud helper and infrastructure companion. This Phase 1 pre-beta presents the fictional **Kairo Labs (Demo)** AWS environment and runs genuine deterministic rules over bundled synthetic data.

No account, AWS credential, API key, customer data, external AI service, or live AWS service is used. The application cannot change infrastructure.

## Current pre-beta scope

RONIN currently provides:

- A responsive infrastructure and FinOps dashboard
- A synthetic inventory for **Kairo Labs (Demo)**
- Synthetic cost totals, service allocation, and six-month cost history
- Four deterministic and explainable analysis rules
- Template-based recommendations derived from rule results
- Read-only demonstration APIs
- A deliberately simple health endpoint
- Local production-style serving through Gunicorn
- Local Docker containerisation

This repository intentionally contains no Terraform, AWS resources, ECS or ECR configuration, Route 53, ACM, GitHub Actions, CI/CD, or deployment configuration.

## Demo-mode safety notice

Everything displayed by this pre-beta is fictional. Resource names, identifiers, utilisation, costs, findings, and recommendations come from the bundled synthetic dataset in `app/data/demo.py`.

RONIN does not request or process:

- AWS access keys, secret keys, or session tokens
- AWS credential files
- Passwords or SSH keys
- Customer infrastructure data
- Personal information
- Uploaded files

The current application makes no AWS API calls and has no infrastructure write operations.

## How the calculations work

The dataset and analysis logic are deliberately separated:

- `app/data/demo.py` contains environment, resource, utilisation, and cost inputs.
- `app/rules/engine.py` evaluates those inputs and produces findings.
- `app/routes.py` exposes the data and calculated findings to the UI and read-only APIs.
- The HTML template presents the results; it does not decide which resources should be flagged.

This makes the rules independently testable and prevents the UI from hiding unexplained decisions.

### Underutilised EC2

A finding named `possible_underutilised_instance` is generated when all conditions are true:

- Service is EC2
- Instance state is `running`
- Average CPU is below 5%
- Observation period is at least 72 hours

Current demo opportunity formula:

```text
estimated opportunity = monthly instance cost × 50%
```

Example: `staging-api-01` averages 1.8% CPU over 96 hours, so it matches the rule.

The 50% factor is an understandable demo assumption, not a provider quotation. The recommendation asks for a review rather than claiming the instance should automatically be stopped.

### Potentially oversized EC2

A finding named `potentially_oversized_instance` is generated when all conditions are true:

- Service is EC2
- Instance is running
- Instance type is one of the larger demo types: `m5.large`, `m5.xlarge`, or `t3.xlarge`
- Average CPU is below 15%
- Average memory is below 25%
- Observation period is at least 168 hours

Current demo opportunity formula:

```text
estimated opportunity = current monthly cost − estimated rightsized monthly cost
```

The estimated rightsized cost is a synthetic input stored with the resource. The recommendation asks the operator to compare and test a smaller class before resizing.

### Unattached EBS volume

A finding named `unattached_ebs_volume` is generated when:

- Service is EBS
- Volume state is `available`
- No attachment is present

Current demo opportunity formula:

```text
estimated opportunity = full monthly cost of the unattached volume
```

This assumes the cost could be avoided after the volume is reviewed and safely removed. RONIN recommends confirming ownership and taking a snapshot where appropriate; it does not delete the volume.

### Cost spike

A finding named `cost_spike_detected` compares the current simulated spend with a historical baseline.

Current formula:

```text
percentage increase = ((current spend − baseline) ÷ baseline) × 100
```

With current spend of £286.40 and a £220.00 baseline:

```text
((£286.40 − £220.00) ÷ £220.00) × 100 = 30.18%
```

The rule triggers because 30.18% is greater than the 20% threshold.

The displayed £66.40 variance is:

```text
£286.40 − £220.00 = £66.40
```

This variance is diagnostic. It is **not automatically a saving** because an increase may be explained by legitimate demand, growth, pricing changes, or newly launched resources.

## How potential savings work

There are currently two related but distinct concepts:

1. **Top-line potential savings:** £74.20/month is a fixed synthetic product-demo value stored in the cost dataset. It exists to reproduce the requested pre-beta scenario consistently.
2. **Finding-level opportunities:** the rules engine calculates an amount for each matching resource using the formulas above.

The current top-line figure is not produced by summing every finding. A simple sum would be misleading because:

- One resource can match more than one rule.
- Underutilisation and rightsizing opportunities can overlap.
- Cost-spike variance is not necessarily avoidable.
- Removing or stopping a resource may involve operational risk.
- Estimated amounts may have different confidence levels.

### Planned production calculation

A future calculation should follow a safer pipeline:

1. Read actual cost and utilisation data locally from the user's authorised AWS session.
2. Normalise costs to the same billing period and currency.
3. Require sufficient observation windows and data completeness.
4. Generate candidate opportunities from independent deterministic rules.
5. Group candidates by resource.
6. Detect overlapping actions, such as stop versus rightsize.
7. Retain only compatible opportunities or choose the most appropriate mutually exclusive action.
8. Exclude pure anomaly variance from guaranteed savings.
9. Apply confidence levels and implementation-risk labels.
10. Present a low-to-high range rather than false precision.
11. Recalculate after the user accepts, rejects, or suppresses recommendations.

A possible future aggregation model is:

```text
resource opportunity =
    selected non-overlapping action estimate
    × confidence factor
    × eligible usage proportion

environment potential savings =
    sum of resource opportunities
    + compatible commitment or scheduling opportunities
```

The calculation should also preserve the raw price source, billing dates, utilisation window, formula, and assumptions so every number remains explainable.

No production AWS integration or production savings model has been implemented in this phase.

## Health score

The current `82/100` health score is a static synthetic value. It demonstrates intended UI hierarchy only.

A future deterministic health model could begin at 100 and apply capped deductions based on factors such as:

- High-severity unresolved findings
- Cost anomalies
- Resource waste
- Missing utilisation data
- Reliability or availability concerns
- Stale findings and suppressed recommendations

Weights, caps, evidence, and recovery behaviour would need to be visible to users and tested before the score could be considered meaningful.

## Deterministic recommendations

RONIN does not call an external LLM. Recommendations are constructed from templates in the rules engine.

For example, the underutilised-instance recommendation inserts:

- Resource name
- Observed average CPU
- Observation duration

This produces conversational output while remaining reproducible, testable, offline, and explainable.

## Local setup

Requires Python 3.12 or newer.

```bash
cd /home/humdaan/projects/RONIN
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt
PORT=8080 python run.py
```

Open `http://localhost:8080/`.

On Ubuntu, install the matching `python3-venv` operating-system package first if Python reports that `ensurepip` is unavailable.

## Health verification

```bash

```

Expected response:

```json
{"status":"ok"}
```

The endpoint has no AWS or other external dependency.

With the development dependencies installed:

```bash
pytest -q
```

The suite covers the health endpoint, major read-only APIs, HTTP hardening headers, rule thresholds, and cost-spike behaviour. It requires no AWS credentials, internet connection, or external API.

## Docker

```bash
docker build -t ronin:local .
docker run --rm -p 80:80 --name ronin ronin:local
curl http://localhost:80/health
```

The image uses dependency-builder and runtime stages, runs Gunicorn as a non-root user, exposes port 80, and excludes test dependencies from the runtime image.

## Security boundary

The pre-beta is read-only and stateless. It has:

- No authentication because it stores no user or customer data
- No AWS SDK
- No credential fields
- No write APIs
- No file uploads
- No arbitrary URL fetching
- No shell or command-execution feature
- No trackers or analytics
- No production debug mode
- A restrictive Content Security Policy and browser-hardening headers

Finding output is educational and must not be treated as production-grade FinOps advice.
